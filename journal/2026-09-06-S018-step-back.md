## What was built

### `timeline.py` — a list and an integer

Stepping back is not running backwards. The steps already happened and are
already recorded, so going back is **moving a cursor over a list**. Stating it
as a property rather than an implementation detail is the point: nothing in
that module calls anything, so there is no side effect to replay, no
non-determinism to worry about, and no way for history to disagree with itself.

It imports nothing from the package, and `tests/test_timeline.py` runs 22 tests
in a millisecond with no sandbox and no child process. The strongest of them
builds a timeline of objects that raise if called and walks it end to end —
"no re-execution" as an assertion rather than a claim.

### The edge is the only hard part

History has an end, and past that end sits a child still blocked mid-run. A
cursor **inside** history is browsing; a cursor **at** the edge is driving.

`LiveRun.forward()` is one verb for both, because a caller should not have to
know which it is doing. Inside history it is a cursor move that never touches
the child; at the edge it continues the run. `browsing` says which, for a
caller that wants to draw the difference.

Appending always jumps the cursor to the edge — a step arriving while the
reader is in the past would otherwise leave the view still while the run moved,
which reads as a hang rather than as history.

### Pausing on the line that raised (exit criterion 2)

`settrace` reports an `exception` event while `f_lineno` is *still the line that
raised it*. That is the only moment at which "pause on the offending line, not
after it" is possible at all — once the frame unwinds, the best anyone can say
is which function failed.

The harness now reports that instant as a step carrying `error`, and then
blocks like any other step, so the parent decides what happens next. Stepping
back from it lands on the same line's *execution* event: "it was about to run
here", then "it raised here". Two events on one line is what actually happened.

`error` rides on the **live event only**. The recorded trace stays exactly
`{line, func, locals}`, because that is what `replay` and `vision` read and a
fourth key would be a second shape for them to know about (D113 held).

```
$ vibecoder boss w1-boss-pipeline --live --solution broken.py
  Drop the cheap stock  above_floor()
     10 ▸ floor = 10.0
     10 ✘ KeyError: 'prise'
```

## Misconceptions and corrections

### M33 — stepping back from a failure lands on the previous line

**Believed:** Writing the test for stepping back off a failing step, I asserted
it would land on line 2 — the statement before the one that raised. That is
what "the previous step" means when you are thinking about lines.

**Revealed by:** The assertion failing with `3 != 2`. The history for a
three-line function that raises on line 3 is: line 2, line 3, line 3. The line
executes and reports, *then* raises and reports again.

**Corrected to:** History is a list of events, not a list of lines, and one line
can produce two of them. Stepping back off the failure gives "it was about to
run here" before "it raised here" — which is more useful than what I expected,
and is the honest account of what happened. The test now asserts both hops.

**Cost:** ~5 minutes. Worth recording because the code was right and the test
was wrong, and the temptation with a failing assertion is to reach for the code
first.

## Friction

- The exception event fires once per frame as it propagates, so a `KeyError`
  inside a comprehension reported twice — two frames of the same file, both
  true, and confusing on screen. Deduplicated in the CLI on `(line, error)`
  rather than in the harness, because two frames raising really is two events
  and the display is what should be opinionated about it.
- `.0` showed up in the locals of every comprehension. It is a genuine local
  and the interpreter's own iterator, not a variable anybody wrote, so the
  harness now filters names starting with `.` alongside `__`.

## Decisions

| # | Decision | Alternatives considered | Rationale | Reversible? |
| --- | --- | --- | --- | --- |
| D118 | History is a cursor over a list, in a module that imports nothing | Rewind by re-executing from the start with a step limit | Re-execution needs determinism and no side effects, which is exactly what T3 W4 has to fight. Read-only history has to fight nothing | no — the waypoint |
| D119 | `forward()` is one verb for browsing and driving | Separate `replay_next()` and `step()` | Callers should not have to track which side of the edge they are on; that is the object's job | yes |
| D120 | Appending jumps the cursor to the edge | Leave the cursor where the reader put it | A run that moves while the view sits still reads as a hang | yes |
| D121 | The failure is reported as a step, on the raising line, and then blocks | Report it in the result and end the run | The `exception` event is the only moment the line still exists. Criterion 2 is about *when*, not about *what* | no |
| D122 | `error` is on the live event only, never in the recording | Add it to the recorded trace | `replay` and `vision` read the recording; a fourth key is a second shape for both (D113) | no |
| D123 | A propagating exception is deduplicated in the display, not the harness | Emit once from the harness | Two frames raising is two events and the harness should say so. Which of them a reader wants to see is a display opinion | yes |
| D124 | Locals beginning with `.` are filtered out | Show every local | `.0` is the interpreter's comprehension iterator: real, and not a variable anybody wrote | yes |
