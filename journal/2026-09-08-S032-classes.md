## What was built

**Six function classes** in [`profiler.py`](../vibecoder/profiler.py), beside
`style_signature`, which already had the right philosophy written into it —
*every threshold here is a judgement about style, never about quality.*

| Class | The habit |
| --- | --- |
| Comprehensionist | you build the result rather than filling one in |
| Loopwright | you write the iteration out, where it can be read and stepped through |
| Architect | you give the data a shape before writing the code that uses it |
| Contractor | you state the contract before the implementation |
| Streamwright | you hand back a stream and let the caller decide how much of it to want |
| Delegator | you reach for the thing that already exists before writing one |

Three signals each — equal counts on purpose, since "cleared 3 of 3" has to
mean the same thing for every class or the comparison that picks a winner is
unfair — and two must land.

### Criterion 6, enforced by signature

*"A player's function class is derivable from the Vibe Vector alone, and
changing their scores without changing their code never changes it."*

`derive_class(vibe)` takes a `VibeVector` and there is **no argument through
which a score could arrive**. That is the enforcement; a test asserts the
parameter list, another greps the source for `mastery`, and a third runs a
hundred observations through a `Mastery` and checks the class is byte-identical
afterwards. There is also a paired negative — changing the *code* does change
the class — without which "scores never change it" would pass for a constant.

The two models live in different modules with no import between them, which is
the same cheap enforcement the mastery/vibe split already uses.

### No class outranks another

`FunctionClass` carries a name, a blurb and its signals. There is deliberately
nothing to sort players by, and a test asserts the field set so that adding a
`rank` or a `score` has to be a decision rather than a drift. Another asserts
no blurb contains a grading word — *better*, *advanced*, *should*, *only* —
because a Loopwright is not a junior Comprehensionist.

### The evidence, and the ties

The hazard is that a class system is a horoscope by default. So `status`
prints the measurement and the line it cleared:

```
  Comprehensionist  you build the result rather than filling one in

  what earned it
    ✔ comprehensions in 70%, at least 45%
    ✔ generator expressions in 52%, at least 25%
    ✔ sum/any/min and friends in 80%, at least 40%

  fits you equally well Contractor, Architect
```

That last line is the part I would defend hardest. On this repository **three
classes clear all three of their signals**, and the winner is decided by margin.
Naming one and hiding the other two would be presenting a coin toss as a
reading — which is exactly what a horoscope does.

## Misconceptions and corrections

### M54 — an empty codebase was a Loopwright

**Believed:** That a class needing two of three signals was a sufficient guard
against handing out labels cheaply. Two thresholds cleared is not a
coincidence, and one is — that was the whole reasoning behind the number.

**Revealed by:** `test_an_empty_codebase_has_no_class`, written as an
afterthought while listing the ways a class system goes wrong. It failed
immediately: `VibeVector()` classified as a **Loopwright**.

The cause is obvious once seen and was invisible while writing the rules.
Loopwright's signals are *comprehensions in at most 15%* and *generator
expressions in at most 10%* — and an empty codebase satisfies both, by having
no code. Two signals met, class awarded. A project with no comprehensions
because it contains nothing is not thereby a Loopwright; it is not thereby
anything.

**Corrected to:** A class needs at least one **positive** signal as well as
its two. Absence can corroborate a reading — a real Loopwright genuinely does
avoid comprehensions — but it can never establish one. `test_absence_alone_never_earns_a_class`
pins it, and a paired test keeps a real Loopwright reachable.

**Cost:** ~5 minutes.

**Generalisable:** The rule counted *evidence* and the failure was that
absence is not evidence of the same kind. A threshold of the form "at most X"
is satisfied by the empty set, by the null hypothesis, by having never tried —
and any scoring system that treats it as interchangeable with "at least X"
will hand out its most confident answer to its least informative input. This
is the same shape as **M1**: free points on an axis measuring nothing, arrived
at from the opposite direction. Worth asking of any predicate: *what does the
empty case score?*

## Decisions

| # | Decision | Alternatives considered | Rationale | Reversible? |
| --- | --- | --- | --- | --- |
| D202 | A class needs at least one positive signal, not merely two of any kind | Two of three regardless of direction | M54. An `at_most` signal is satisfied by an empty codebase, so absence alone would earn the most confident label from the least informative input. | Yes |
| D203 | `derive_class` takes a `VibeVector` and nothing else | Pass the whole `Session` and read the vector from it | Criterion 6 becomes a property of the signature rather than a rule someone must remember. Enforcement by argument list is the cheapest kind there is. | No — it is the criterion |
| D204 | Every class has exactly three signals | Let each class have as many as its habit suggests | "Cleared 3 of 3" has to mean the same thing across classes, or ranking by signals met silently favours whichever class was given fewest. | Yes |
| D205 | Equally good fits are printed beside the winner | Show only the class awarded | Three classes clear every signal on this repository and the winner is decided by margin. Hiding that presents a coin toss as a reading, which is the horoscope the hazard names. | Yes |
| D206 | A codebase that does not lean gets `None` | A default class such as "Generalist" | A default class is a label nobody earned, and "your code does not lean hard enough in any one direction to name" is a description rather than a gap. | Yes |
| D207 | Classes live in `profiler.py`, not with mastery | A new `classes.py`; alongside `policy.py` | It reads the Vibe Vector and belongs with `style_signature` and `derive_tags`, which do the same. Keeping it out of the mastery module means the two layers cannot be blended by accident. | Yes |
