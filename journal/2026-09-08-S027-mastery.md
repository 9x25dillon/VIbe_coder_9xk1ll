## What was built

T4 starts. W1, W2 and W3 landed; W4 — the selection policy — is next and is
the first waypoint whose design is genuinely open.

### W1 — mastery, in a module that imports nothing

[`mastery.py`](../vibecoder/mastery.py) holds a per-tag competency estimate
and the rule that moves it. It is a separate module from `models.py` for the
reason [`fight.py`](../vibecoder/fight.py) is: this is a model *with rules* —
a confidence threshold, an update step, a decay still to come in W6 — and
those rules have constants that need explaining. `models.py` holds shapes.

It imports nothing, which cost one design decision: the update rule takes
plain numbers rather than a `ScoreBreakdown`, and `session.py` does the
unpacking. That is the same trade `score_fight` made in S024, taking
`repairs_spent: int` rather than a `Fight`.

**An estimate carries its evidence.** `value` alone cannot be read honestly —
0.5 after four runs is a measurement, 0.5 after none is the absence of one —
so `observations` sits beside it and `confident` exists so a caller cannot
forget which it is holding. That is T4's tag-sparsity hazard made
unforgettable rather than merely documented: with 14 tags across 12 levels,
`recursion`, `regex` and `numeric` each appear on exactly **one** level, so a
single lucky run would otherwise steer content on its own.

### W2 — a dial that does not move the default

`Level.tests_for(seed, difficulty)` passes a `Difficulty` to `make_tests` only
if the generator's signature accepts one. Authors opt in one level at a time,
and detection is by inspection rather than by a flag on the `Level` — a flag
would be a second place to keep in sync with the function it describes, and
the function is the thing that is actually true.

The constraint that shaped the whole waypoint: **the default difficulty has to
reproduce pre-difficulty data byte for byte.** Every op count in
`data/baselines/` was measured before the parameter existed. A level that
shifted under the default would quietly turn those files from evidence into
decoration, and `test_records` would only notice for levels whose reference op
count happened to change. So `Difficulty()` is 0.5, authors pick ends that
straddle their old constants, and it is asserted for every level and every
boss step rather than trusted.

That constraint also produced the session's one genuinely fiddly detail.
`scale(0.15, 0.45)` at the midpoint is `0.30000000000000004`, not `0.3` — a
4e-17 difference, which would change a `rng.random() < rate` outcome with
probability around 1e-14. Effectively never, and "effectively never" is not
"identical", which is the standard a baseline has to hold to. Scaling a whole
percentage instead — `scale(15, 45) / 100` — is exact, and reads better in the
explanation W7 will have to generate.

`w2-l2-groupby` is the first level to opt in, which is the one the trajectory
names. Gentle generates 228 rows with 14% holes; hard generates 532 with 45%.

### W3 — the update rule, in the one place practice never reaches

```
observed = 0.5·(accuracy/100) + 0.3·(functional/100) + 0.2·first_try
value   += 0.3 · (observed − value)
```

Applied inside `Session.submit`. That is the whole of exit criterion 5:
`cmd_play` skips `submit` entirely when there is no honest solve time — the
same branch that drops the Speed axis, for the same M1 reason — so "practice
does not move mastery" is a consequence of one branch rather than a second
rule someone has to remember. Two tests pin that `submit` is the *only*
writer, so if another method ever learns to move mastery, criterion 5 stops
being structural at the moment it is noticed rather than months later.

**Speed is deliberately not an input.** Solve time measures a session, not a
competence; a player interrupted by a phone call is not worse at recursion
afterwards. The signature is the assertion — there is nowhere to pass it.

## Misconceptions and corrections

### M47 — the forward-compatibility fix was applied one level too low

**Believed:** That profiles were safe against being opened by an older build.
S015 established exactly this problem for the `VibeVector` — an old build
dropped unknown fields on load and destroyed them on save, silently, on an
ordinary `vibecoder status` — and fixed it with an `unknown` dict that
round-trips verbatim. I assumed the lesson had been applied.

**Revealed by:** Checking before adding a new top-level key, because W1 adds
`mastery` to the profile and I wanted to know what an older build would do
with it. `Session.load` reads a fixed list of keys and `Session.save` writes a
fixed payload, so **the envelope around the vector had the bug the vector had
been fixed for.** A player alternating between two builds would lose their
entire mastery vector on an ordinary command.

**Corrected to:** `Session` now carries the same `unknown` dict, merged on
save with known keys winning. Four tests, including repeated round trips —
once is luck; the failure being guarded is a player using two builds for weeks.

**Cost:** ~10 minutes, and it was found rather than suffered. It had been
latent since S015 because nothing had added a top-level key since.

**Generalisable:** A fix applied to a *type* does not protect the container it
travels in. The vector's `unknown` dict was written, tested and documented,
and the reason it looked complete is that the vector was the only thing that
had ever changed shape. **The next thing to change shape is where the same bug
reappears** — worth asking, whenever a fix is scoped to one class, what else
sits on the same path.

### M48 — "effectively never" is not the standard a baseline holds to

**Believed:** That scaling the missing-data rate as `scale(0.15, 0.45)` was
fine, because at the midpoint it is 0.30000000000000004 and the chance of a
`rng.random()` draw landing in that 4e-17 window is about 1e-14 across every
row of every seed.

**Revealed by:** Writing down what "the default reproduces the old data" is
*for*. The baseline exists so that a change to the instrumentation or a
generator is visible; a guarantee that holds with probability 1 − 1e-14 is a
guarantee that fails silently and rarely, which is the worst available failure
mode for a regression detector. A test that flakes once a decade is worse than
one that never passed.

**Corrected to:** Scale a whole-number percentage and divide — `scale(15, 45)
/ 100` is exactly 0.3. It also reads better in the explanation W7 will have to
generate: "30% of rows missing" rather than "30.000000000000004%".

**Cost:** ~5 minutes, before it was written.

## Friction

Moving `Mastery` out of `models.py` after having written it there, mid-session,
including its tests. It was the right place for a *shape* and the wrong place
for a model with rules, and the `fight.py` precedent had already settled the
question — I just did not consult it until the update rule needed somewhere to
live. Cheap now, and it would not have been after three more waypoints landed
on it; T4 has eight left and W6, W9 and W11 all touch this module.
