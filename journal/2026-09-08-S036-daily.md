## What was built

**[`daily.py`](../vibecoder/daily.py)** — one level and one variant seed from
the date alone, and `vibecoder daily` to show or play it. Like `fight.py`,
`mastery.py` and `timeline.py`, it **imports nothing**: it is handed the level
ids rather than reaching for the registry, so the selection is testable against
any catalogue including the empty one.

### The waypoint's own wording was the bug

W1 is written as `hash(date)` → variant. That is exactly what it must not do.

```
$ for i in 1 2 3; do python3 -c "print(hash('2026-09-08'))"; done
-7723537222559262413
-7920657940426615118
 1873428733625979326
```

Python randomises `str` hashing per process unless `PYTHONHASHSEED` is pinned.
Exit criterion 1 asks two *machines* to agree, and `hash` cannot manage two
invocations on one. `hashlib.sha256` is specified, stable across builds and
platforms, and in the standard library, so it costs nothing under N1.

The failing behaviour is kept as a test — `test_builtin_hash_would_not_have_been`
— so the next person to read the waypoint and reach for the obvious thing sees
why it does not work rather than being asked to trust a comment.

### A daily is not adapted, which reverses T4 deliberately

`Daily` carries no difficulty field, and that is the whole design.

T4 spent eleven waypoints learning to give each player a variant matched to
them. A shared challenge needs precisely the opposite: **adapting a daily
hands two players different data for the same puzzle**, and the leaderboard
W2–W4 are building toward would be comparing different problems while calling
them one.

So `cmd_daily` imposes the standard difficulty, `cmd_play` honours it, and the
screen says so:

```
  [STANDARD] a daily challenge is the same for everyone, so this variant
             is not adapted to you
```

The absence of the field is the enforcement; the sentence is so a player is
not left wondering why the adaptation they were promised stopped working.

The test for this has a paired negative — without it, "two opposite profiles
get the same variant" would also pass for a difficulty dial that had simply
broken.

## Decisions

| # | Decision | Alternatives considered | Rationale | Reversible? |
| --- | --- | --- | --- | --- |
| D225 | `hashlib.sha256`, not `hash()` | The waypoint's literal wording; pinning `PYTHONHASHSEED` | `hash` is randomised per process, so the same date differs between two runs on one machine. Pinning the env var would make correctness depend on how the game is launched. | No — it is criterion 1 |
| D226 | `daily.py` imports nothing and is handed the level ids | Reach for `level_registry` inside | Same discipline as `fight.py` and `mastery.py`: the selection is then testable against any catalogue, including empty. | Yes |
| D227 | A daily has no difficulty field, and `cmd_play` accepts an imposed one | Let the daily adapt like any other level; a separate play path | Adapting a shared challenge gives two players different data for the same puzzle. The absent field is the enforcement, and a separate play path would mean a daily was scored by different machinery. | No — it is criterion 1 |
| D228 | Ids are sorted before indexing | Use registry order | Otherwise an ordering bug elsewhere silently changes what everyone plays today. | Yes |
| D229 | Determinism is scoped to the date *and the build's level set* | Pin a catalogue snapshot in code | A pinned snapshot rots against the levels that actually exist. Two machines on the same build agree, which is what the criterion asks. | Yes |

## Handoff

- **State:** T5 is `IN FLIGHT`; **W1 `LANDED`** and **exit criterion 1
  verified**. The daily is the same level and variant for everyone, derived
  with `hashlib` rather than the `hash()` the waypoint names, and deliberately
  not adapted to the player. 1362 tests green unpinned, 1338 pinned, `verify`
  clean on 54 reference runs.
- **⚠ Use Python 3.11 on this machine** — see M5 in S003. Unchanged.
- **Next action: T5 W2**, the local leaderboard and personal daily history.
  The trajectory is explicit that it should be *"playable and useful with no
  backend at all"*, so it is a `Session` concern rather than a network one —
  and `Session` already stores per-level history that a daily record can sit
  beside. Note M47 before adding the field.
- **After that, W3 needs a server**, which is the first thing in this project
  that does. Read T5's hazards first: client-reported scores are claims, and
  **Speed cannot be verified at all** — the trajectory already suggests
  ranking dailies on Accuracy + Functional only.
- **Do not go near W5 or W6 yet.** The hard gate (T2 W1–W3 landed) is
  satisfied, and T5's own hazard says it is *necessary and not sufficient*: a
  level is an importable module whose `make_tests` runs in the **parent**
  process, so both bypass `run_code` entirely. Sharing a level needs a data
  format before it needs a container.
- **Blockers:** none for T5 W2–W4. T2 W4 remains blocked on a registered OAuth
  application.
- **Context required:** M12 in S006 before touching level loading. Q97 is
  still the largest gap in the project: **T4's eleven waypoints have never
  been played by a person**, and now T5 W1 joins them.
