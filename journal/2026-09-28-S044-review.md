## Review of S042–S044

### Where the assistant lost time

1. **The URL was asked before the host was read.** `/vibecoder/` was offered as
   a free choice, the whole deploy path was written around it, and reading the
   server later showed its header gate made the subpath a loosening of the
   landing page (M65). The site's CSP header, already fetched at the start, was
   the clue; `curl -I` of the apex plus one question about how the site was
   built would have put the subdomain on the table in the first round.
2. **The phone was attached from the first minute and used last.** A full
   headless screenshot tour was built and reviewed before the first device
   install, and the device found the one bug the tour could not (M63). One
   early install of a bare build would have caught it an hour sooner.
3. **Shell assumptions cost a dozen retries.** The environment said fish; the
   shell was zsh. Unmatched globs aborted a command, `=====` was expanded, an
   unquoted variable was not word-split, and piping a test run through
   `tail -4` hid which test failed and forced a second 90-second run. Checking
   `$0` once and saving full logs to a file would have removed all of it.

### Where the user's input would have saved time

1. **Prerequisites were discovered, not stated.** The first request asked for
   PyPI publishing and a deploy to a named domain; there was no PyPI account,
   the SSH user was `astra` rather than `root`, and the firewall did not admit
   this host. Each surfaced as a blocker hours in. A line such as "no PyPI
   account; I deploy as astra@host; SSH is IP-restricted" up front would have
   reshaped the plan immediately.
2. **Status updates without the state.** "try it now" and "okay" arrived after
   firewall changes whose content was unknown, and the first one had
   allow-listed the server's own address. "Allowed 72.105.230.138 on TCP 22" is
   checkable before a connection is even attempted.
3. **The one human-only gate is still open.** T9 W6 is a person playing the
   phone build. It could have run in parallel with the documentation work, and
   it is the only evidence nothing automated can produce.

### Prompting that would use the assistant better

- State **done**, not just the goal: "done = APK installed on my Pixel, game at
  <url>, payments backend untouched".
- State **what you have and do not have**: accounts, keys, access, budgets.
- Say **which decisions you delegate** ("pick the URL layout yourself") and
  which you want asked; it removes a round-trip per question.
- Use the repo's own vocabulary — waypoint, exit criterion, "land T9 W6" — so
  a request maps to a record without translation.

### Vocabulary

- **Origin** — scheme + host + port, e.g. `https://vibecoder.astra-arcana.com`.
  It is the unit browsers isolate by: storage, service-worker scope, and in
  practice a security policy all attach to an origin, not a path. "Give it its
  own origin" was the whole answer to M65.
- **Blast radius** — everything a change can break if it goes wrong. The
  deploy kept it small on purpose: only the frontend container was rebuilt, the
  backend was never restarted, and DNS was read before it was written. "Keep
  the blast radius to the frontend" is a one-line constraint worth giving.

## Misconceptions and corrections

### M67 — An unmerged branch is unmerged work

**Believed:** `git branch --no-merged main` listing `feat/terminal-cockpit`
meant work was waiting to be merged, as the request to "merge" assumed.
**Revealed by:** `git cherry -v main feat/terminal-cockpit` marking its only
commit `-`, an identical patch already on `main` under another hash.
**Corrected to:** the branch is stale; merging would add a redundant merge
commit and nothing else. **Cost:** none, caught before acting. **Lesson:**
"not merged" compares commit ids; `git cherry` compares the changes.
