### One shot, enforced without a server

The first completed run of a date is the **ranked** one. A replay is recorded
— it happened — and never replaces the score that counts.

That is worth having now rather than at W3, because it is the rule a
leaderboard depends on and it needs no backend to enforce. The player is told
before they start and again after, rather than discovering it from a number
that failed to move:

```
  [ALREADY PLAYED] you scored 114.0 on this one. Playing again is recorded
                   but does not replace it.
    [DAILY] recorded as a replay -- your ranked score stands
```

### Q99, answered: record what was served

An `Attempt` stores the level and seed it was **actually played with**, never
re-derived.

`choose` depends on the build's level catalogue, so adding a level changes
which one a past date selects. A history that recomputed would quietly rewrite
what you played — and a board comparing two builds would be comparing two
puzzles while showing one date. The test demonstrates the drift rather than
asserting it: the same date against a catalogue with one more level picks
something else.

### Criterion 5, held structurally

*"Leaderboards remain usable offline, degrading to local-only."*

There is nothing to degrade from. `board` reads a list and reaches for
nothing, `daily.py` imports no package at all, and a test asserts that — so
the module cannot acquire a network dependency by accident. W3's server
becomes an **overlay on top of** the local board rather than the source it
falls back from, which is the difference between offline working and offline
being remembered.

  daily is the same for everyone, its history records what was actually
  served, the first run of a date is the one that counts, and the board is

  `verify` clean on 54 reference runs.
- **⚠ Use Python 3.11 on this machine** — see M5 in S003. Unchanged.
- **Next action: T5 W3**, score submission with server-side re-verification —
  **the first thing in this project that needs a server.** Read T5's hazards
  before designing it. Two are load-bearing:
  - *A client-reported score is a claim, not a fact.* The server must re-run
    the submission, which means it needs the sandbox — so W3 is where T2's
    work stops being about profiling other people's code and starts being
    about running it on our own machine.
  - **Speed cannot be verified at all.** Wall-clock solve time is
    unfalsifiable, and the trajectory already suggests ranking dailies on
    Accuracy + Functional only, treating Speed as a personal statistic. That
    is a scoring-weight decision and therefore **the user's call** (§12).
  - N1 applies: a server means `http.server`, not a framework.
- **Blockers:** none for T5 W3–W4. T2 W4 remains blocked on a registered OAuth
  application.
- **Context required:** D230 before touching the daily history. Q98 (does a
  daily bank into mastery — it does today) becomes real once scores are
  compared between players.
