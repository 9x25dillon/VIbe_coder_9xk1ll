## What was built

Eleven modules under [`vibecoder/`](../vibecoder/), six levels, 127 tests (112 for the engine, 15 for the record system).

**The execution boundary.** [`_harness.py`](../vibecoder/_harness.py) runs in a
separate interpreter and talks JSON over stdin/stdout. It never imports the
`vibecoder` package, which keeps the child's import surface to the standard
library and means a broken game module cannot corrupt a run. The parent
([`runner.py`](../vibecoder/runner.py)) enforces a wall-clock timeout the child
cannot escape; the child additionally sets `RLIMIT_AS` and `RLIMIT_CPU` where
the platform allows.

**Op counting is the interesting decision.** The Functional axis needs a
deterministic efficiency measure, and wall-clock time is far too noisy at these
scales. The harness counts *line executions inside the submitted file only*,
filtering `sys.settrace` events by code filename. A call to `sorted()` therefore
costs one op while a hand-written sort costs hundreds. That is not a complexity
measurement and is documented as such — but it is exactly the lesson the game
wants to teach, and it is stable run to run.

Each test case runs twice: once untraced for honest timing and memory, once
traced for the op count. Tracing roughly doubles runtime, so measuring both from
one pass would corrupt the timing.

**Levels generate their data.** A level supplies `make_tests(rng)` rather than a
fixed list, so seed 1 and seed 2 are different puzzles with the same shape. This
is what makes the design's replayability claim real rather than cosmetic, and
[T4](../docs/trajectories/T4-adaptive.md) will reuse the same machinery to vary
difficulty instead of swapping problems.

Reference solutions are benchmarked against **the same generated data the player
faces**, cached per `(level, seed)`. Benchmarking against a fixed dataset would
mean a variant with 10× the rows gets scored against the wrong baseline.

**The profiler never executes anything.** [`profiler.py`](../vibecoder/profiler.py)
is pure `ast` walking. Given that its input is other people's repositories, this
is a security property, not a stylistic one.

**Tips are deliberately conservative.** A tip that fires on good code is worse
than no tip, because it costs the player's trust in every later tip. Each rule
matches a narrow syntactic shape, rules that raise are swallowed rather than
breaking the game, and there is a test asserting that idiomatic code produces
*zero* tips.

**The record system is enforced, not aspirational** (objective 8, added
mid-session). [`docs/trajectories/`](../docs/trajectories/) holds the forward
plan, this journal holds the backward record, and
[`data/`](../data/) holds both as machine-readable JSON. The part that makes it
more than good intentions is [`tests/test_records.py`](../tests/test_records.py):
15 tests asserting that every session record validates against its schema, that
every journal entry has a data twin and vice versa, that session ids are
contiguous, that every referenced trajectory exists, and that **every relative
Markdown link in the repository resolves**.

Schema validation is a ~40-line subset of JSON Schema implemented in the test
file rather than a dependency, because the zero-dependency rule applies to tests
too. The link checker found a broken link on its first run — a placeholder in
`TEMPLATE.md`, which is now excluded by name rather than by weakening the check.

The most useful test in that file is
`test_recorded_op_counts_still_reproduce`, which re-runs every reference against
the committed [baseline](../data/baselines/2026-08-08-t1-reference-baseline.json).
If it fails, either a reference changed, a level's generated data changed, or
the op-counting instrumentation changed — all three are worth being told about
rather than discovering through a player's confusing score.

## Misconceptions and corrections

### M1 — Scoring a file from disk can reuse the interactive timing path

**Believed:** `--solution` could share the same clock as interactive play, with
elapsed time measured from process start.

**Revealed by:** Running a deliberately terrible O(n·m) join through it. It
scored **95.8 and three stars**. The clock had been running for about 40
milliseconds, so the Speed axis paid out a full 100 for work that took no time
because it had not been done in that process.

**Corrected to:** There is no honest solve time when scoring a file, so the axis
must not be scored at all. `Weights.without_speed()` renormalises accuracy and
functional to sum to 1 while preserving their 2:1 ratio, and practice runs are
not banked to the profile. A front-end that genuinely tracks solve time passes
`--elapsed` and gets a fully ranked run.

**Cost:** ~20 minutes. Cheap, and only because the naive solution was run
adversarially rather than assumed to score badly. The general lesson — *test the
scoring system with a bad solution, not just a good one* — is the most portable
thing this session produced.

### M2 — Pattern frequency can be normalised by dividing by file count

**Believed:** `min(1.0, occurrences / files)` gives a reasonable 0–1 share for
file-level patterns.

**Revealed by:** Self-profiling. Four separate patterns reported exactly 100%,
including `try_except` and `fstring`. Any pattern appearing more than once per
file on average pins to the cap and carries no signal at all — precisely the
common patterns that most need discriminating.

**Corrected to:** File-level patterns are now *share of files containing the
pattern*, which is bounded by construction and stays interpretable at any
codebase size. Per-function patterns (`decorator`, `type_hints`, `recursion`,
`async`) keep a per-function denominator, since "share of functions that are
decorated" is a meaningful quantity while "share of files containing a
decorator" is not. Post-fix the same codebase reports a usable spread:
type_hints 97%, f-strings 89%, comprehensions 78%, try/except 44%, classes 28%.

**Cost:** ~15 minutes. Would have shipped silently and quietly degraded every
downstream personalisation decision, since saturated patterns cannot earn tags.

### M3 — `submit()` could take a single score multiplier

**Believed:** One multiplier argument per submission was enough.

**Revealed by:** Writing the call site. Multipliers are per-world, so applying
one submission's multiplier to *every* level's banked best silently rescaled the
global total on each save.

**Corrected to:** `submit()` takes a `multipliers` mapping; unknown levels
default to 1.0 so a profile referencing a deleted level still totals cleanly.
Caught before running, unlike M1 and M2.

## Friction

- **No pytest available**, so the suite is stdlib `unittest`. This turned out
  to be a feature rather than a limitation and is now a deliberate constraint:
  the game runs anywhere a Python interpreter does. `subTest` covers the
  parametrisation that would otherwise want fixtures.
- **Two-pass execution is a real cost.** Every test case runs twice. Fine at
  current sizes; it will need attention when boss fights run longer programs
  under trace.
- **Colour output is hard-coded ANSI.** Adequate for a prototype, wrong for
  anything embedded. Noted, not fixed.

## Decisions

| # | Decision | Alternatives considered | Rationale | Reversible? |
| --- | --- | --- | --- | --- |
| D1 | Count traced line executions as "ops" | Wall-clock time; bytecode counting; big-O annotation by hand | Deterministic, zero-dependency, and rewards builtins — which is the lesson | Yes, isolated in `_harness.py` |
| D2 | Subprocess isolation rather than containers | Docker from day one | Phase 0 runs the player's own code on their own machine; containers are [T2](../docs/trajectories/T2-sandbox.md)'s job, and blocking on Docker would have stopped the core loop being testable today | Yes, `run_code` signature is the seam |
| D3 | Seeded test generation instead of static fixtures | Fixed test lists per level | Replayability becomes real, and T4 gets its difficulty knob for free | Hard to reverse — level API |
| D4 | Practice mode drops Speed rather than faking it | Award 100; award 0; require `--elapsed` always | An unmeasurable axis must not be scored; renormalising keeps the rest meaningful | Yes |
| D5 | Bonuses can push a total above 100 (max 120) | Cap at 100 | The design specifies percentage bonuses on top; capping would make first-try success worthless to a strong player | Yes, one line in `scoring.py` |
| D6 | No third-party dependencies at all | pytest, radon, pylint as the design suggested | Portability, and every metric stays inspectable rather than borrowed | Yes |

## Handoff

- **State:** [T1](../docs/trajectories/T1-core-loop.md) is `LANDED` — all six
  exit criteria verified. `vibecoder/` holds 11 modules and 6 levels across 2
  worlds; 127 tests green; `verify` clean on 18 reference runs. No boss fights.
  No network code anywhere. Profile state lives at `$VIBECODER_HOME` or
  `~/.vibecoder`.
- **Next action:** [T2 W1](../docs/trajectories/T2-sandbox.md) — put a
  container-backed runner behind the existing `run_code` signature, keeping
  `_harness.py` as the in-container entrypoint. The signature is already the
  seam; nothing above `runner.py` should need to change.
- **Blockers:** none for T2 W1–W3. T2 W4 (GitHub OAuth) needs a registered
  OAuth application and a decision on where profiling runs — locally, or
  server-side. That decision has a privacy consequence and should not be made
  incidentally.
- **Context required:** [`docs/SCORING.md`](../docs/SCORING.md) before touching
  any weight or curve; [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) for the
  module boundaries; M1 above before altering how Speed is measured.
