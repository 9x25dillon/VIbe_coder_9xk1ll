## What was built

Before this session the sandbox was one layer: namespaces. Good ones — the
network was gone and the host filesystem was not in the mount namespace — but
one layer, and a layer made of configuration. Configuration can be wrong in a
way that still looks like it worked.

[`vibecoder/seccomp.py`](../vibecoder/seccomp.py) is the second layer, and it
removes the *ability to ask*. Under it a submission cannot open a socket at
all, rather than opening one that goes nowhere, and cannot reach `ptrace`,
`unshare`, `setns`, `mount`, module loading or `bpf`. The two layers fail
differently, which is the whole reason for having both: a namespace is
something we set up, and this is a refusal from the kernel that does not
depend on our having set anything up correctly.

The filter is written out longhand because `libseccomp` is a dependency and N1
forbids it. A seccomp filter is classic BPF — a list of 8-byte instructions —
so generating one is a page of `struct.pack`. The syscall numbers were read
from this machine's `asm/unistd_64.h` and `asm-generic/unistd.h` rather than
recalled, because a wrong number fails in the worst available way: silently
permitting the thing it was written to deny. The filter checks the
architecture first and kills the process on a mismatch, since a syscall table
applied to the wrong architecture is not a weaker filter, it is a filter that
blocks unrelated syscalls and lets the intended ones through.

Denials return `EPERM` rather than killing. The submission sees a
`PermissionError`, and the harness records it as a failed test with a readable
message — which is how exit criterion 1's "and the attempt is recorded" is
satisfied, by the machinery that already reports every other error rather than
by a new one.

**The seam grew a shape it did not have.** `bwrap --seccomp` takes a file
descriptor, not a path, so a backend can no longer be fully described by an
argv. `Backend.launch()` is now a context manager yielding a `Launch` — argv,
`pass_fds`, and the list of protections actually applied — so the parent can
hold the program's descriptor open across the spawn. The `hardening` tuple is
reported by `vibecoder sandbox` rather than assumed, because a protection that
is claimed and absent is worse than one that is known to be missing.

Three other changes, each from something measured rather than planned:

- **Non-root.** The submission ran as the player's own uid inside the user
  namespace. It is now 65534. Nothing exploitable followed from uid 1000
  today, but every bind mount added by a future waypoint would have been
  writable by default rather than by decision.
- **`RLIMIT_NPROC`.** A fork bomb was previously contained only by the wall
  clock. The limit is applied by the harness but decided by the parent and
  sent in the payload, because `RLIMIT_NPROC` counts processes per real uid —
  on the host path it would count the player's whole login session and fail
  instantly. It is only safe where the submission owns a uid, which is exactly
  what an isolating backend provides.
- **The interpreter moved to `/python`.** See M9.

## Misconceptions and corrections

### M9 — Mounting the interpreter at its own path is neutral

**Believed:** Binding `sys.base_prefix` to the same path inside the sandbox was
a detail. The submission needs an interpreter; where it appears is arbitrary
and the host path is the convenient choice.

**Revealed by:** An escape test asserting the player's home directory was
unreadable — which failed. The sandbox could `listdir('/home/kill')`.
Bubblewrap creates the parent directories a bind needs, and this machine's
interpreter lives at `/home/kill/.local/share/uv/python/…`, so mounting it
conjured `/home/kill` into the sandbox. The directory was empty and the real
contents were never readable; what leaked was the *shape* of the host — the
player's username, and where their tools are installed.

**Corrected to:** The prefix mounts at a fixed `/python`, and the guest
interpreter path is derived from it. `/home` no longer exists in the sandbox
at all. The sandbox is now identical whether the interpreter came from the
system or a user-local install, which is a better property than the one being
fixed.

**Cost:** ~20 minutes. Worth recording that the first instinct was to fix the
*test*, since `os.path.expanduser('~')` inside the sandbox resolves to `/work`
and the original test therefore proved nothing either. Both were true: the
test was weak *and* there was a real leak behind it. Fixing the test alone
would have closed the only thing that was going to find this.

### M11 — Docker's default seccomp profile is good enough

**Believed:** `DockerBackend` could report `seccomp` in its hardening because
Docker applies its default profile unless told otherwise, and that profile
already covers this module's list.

**Revealed by:** Running the full suite under `VIBECODER_SANDBOX=docker`, which
failed `test_ptrace_is_denied`. Docker's default profile permits `ptrace`
deliberately, so that debuggers work inside containers. The bubblewrap backend
denied it and the Docker backend did not, while both reported the same word.

**Corrected to:** `seccomp.docker_profile()` emits the same denial list in
Docker's JSON dialect, shipped with `--security-opt seccomp=`. Docker names
syscalls rather than numbering them, so that form needs no architecture table
at all — the same policy, written twice, in the two dialects the two backends
speak.

**Cost:** ~25 minutes, and it is the most important finding of the session.
The claim was written in the same commit as `TestHardeningIsReported`, a test
class whose entire purpose is "a protection that is not applied must not be
claimed" — and it only checked bubblewrap. Writing the rule down is not the
same as enforcing it. What actually caught this was running the suite under a
backend I was not developing against, which is why the gate is now cloned per
backend: **an adversarial suite that exercises one of two backends is a gate
with a hole in it.** The hole was open for the length of one session because
nothing was looking.

### M10 — Containing a fork bomb is a matter of limiting forks

**Believed:** `RLIMIT_NPROC` would turn a fork bomb into a clean, diagnosable
`EAGAIN`.

**Revealed by:** It turned it into `SandboxCrash: sandbox returned malformed
output` — a *worse* failure than the timeout it replaced, and one that exit
criterion 3 explicitly rules out by asking for a diagnosable error. The forks
that succeeded before the limit bit inherited stdout and ran on to the end of
the harness, each writing its own JSON reply into the same stream.

**Corrected to:** The harness records its own pid at startup and any descendant
reaching the write leaves via `os._exit(0)` — no reply, and no interpreter
shutdown flushing buffers into a stream the parent is parsing. One JSON reply
per run is the entire contract with the parent, and nothing before this
enforced it.

**Cost:** ~15 minutes. The generalisable part: a resource limit changes what a
program does *after* it hits the limit, and the interesting behaviour is
usually there rather than at the limit itself. The fix is not about forking at
all — it is about a contract on stdout that had been holding by luck.

## Friction

- Watching the probe output before writing any code was worth more than
  anything else this session. Three of the four real changes — uid, `unshare`,
  socket creation — came from a table of what the sandbox actually did, not
  from reading the waypoint.
- The escape suite failed hard when `VIBECODER_SANDBOX=subprocess` was pinned,
  because a pin wins over the untrusted flag by design (D13). Correct, and
  confusing; it now skips with a reason instead. A skipped security suite
  should read as louder than a passing one.
- Two filesystem tests failed under Docker for a reason that was not a
  vulnerability: a container brings its own `/etc/passwd` and its own `/`, so
  "the path is absent" is true under bubblewrap and false under Docker while
  both are equally safe. They now assert that the *host's* content is
  unreachable — the host username, the repository's own absolute path —
  which is the property a player actually cares about and which holds under
  both models.
- The suite went from 13s to 43s, almost entirely the Docker pass of the gate
  running a cold container per attempt. N8 justified itself with "it runs in
  four seconds", which had stopped being true; the rule is unchanged and its
  justification now names the real number, with a pinned inner loop for
  working. A stale justification is how a rule stops being believed.

## Decisions

| # | Decision | Alternatives considered | Rationale | Reversible? |
| --- | --- | --- | --- | --- |
| D24 | Hand-assemble the BPF filter | `libseccomp`; no seccomp at all | N1. A filter is a page of `struct.pack`, which costs less than the dependency | yes |
| D25 | Syscall numbers read from this machine's headers | Recall them; copy a published list | A wrong number silently permits what it was meant to deny | no |
| D26 | Denials return `EPERM`, not `SECCOMP_RET_KILL` | Kill the process | The submission raises `PermissionError`, which the existing machinery records — criterion 1's "recorded" half | yes |
| D27 | An unsupported architecture disables seccomp rather than blocking the run | Refuse to run untrusted code without it | Namespaces still hold; `hardening` reports the gap instead of hiding it | yes |
| D28 | `Backend.launch()` is a context manager yielding a `Launch` | Return argv plus a global fd registry | `--seccomp` needs a descriptor held open across the spawn; the context manager owns its lifetime | no |
| D29 | The parent decides `RLIMIT_NPROC`, the harness applies it | Always apply it in the harness | It counts per real uid, so on the host path it would count the player's whole session | no |
| D30 | The interpreter mounts at a fixed `/python` | Bind it at its host path | M9: binding under `/home/someone` conjures that path into the sandbox | yes |
| D31 | The escape suite skips when no isolation is in effect | Fail; or ignore the pin | There is nothing to assert without isolation, and a skip is louder than a pass | yes |
| D32 | Every attack runs against every isolating backend | Test whichever backend is selected | M11: a gate that exercises one of two backends is a gate with a hole in it | yes |
| D33 | Ship our own seccomp profile to Docker | Rely on Docker's default profile | Its default permits `ptrace` on purpose, so relying on it made the two backends differ while reporting the same hardening | yes |
| D34 | A pinned backend narrows the gate to that backend | Always run every backend | Gives a 17s inner loop without a mode that skips the gate entirely; unpinned remains what CI runs | yes |
| D35 | Filesystem attacks assert host content is unreachable, not that paths are absent | Assert paths do not exist | The two backends have different filesystem models; the property players care about is that *their* machine is unreadable | yes |
