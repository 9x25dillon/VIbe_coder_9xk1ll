## What was built

### The format, and the trap it avoids

A boss is *n* linked functions rather than one big one. The obvious way to link
them — feed step one's output into step two's tests — is the trap: a mistake in
step one would then fail step three, which teaches the wrong lesson and scores
one mistake three times.

So **each step is graded against its own tests**, with canonical inputs. The
linking is real anyway, because the steps share **one source file** and a later
step may call an earlier function by name. That file is the "shared state" the
design asks for, and it is a plain Python module rather than a bespoke
namespace, so a later step calling an earlier function is ordinary code rather
than a framework feature.

The cascade problem then dissolves on its own: steps unlock in order, so by the
time step three runs, step one has already passed its own tests. Calling it is
safe because it has been checked, not because anything special protects it.

### Enforcing the link

A step declares what it builds on (`uses=("parse_rows", "above_floor")`). That
is documentation for the player and a contract against the *reference* — never
a constraint on the player, who may solve it any way that passes.

Three contract tests make the link real rather than decorative:

- the reference must actually **call** what it declares, checked by walking the
  AST;
- a declared dependency must name an **earlier** step, because depending on a
  later one is a cycle the unlock order cannot serve;
- a linked step's reference must **fail in isolation**. If it passes without the
  steps it builds on, it never needed them, and the boss is three unrelated
  levels wearing one name.

`BossLevel.__post_init__` refuses a boss with fewer than two steps, duplicate
step ids, or two steps sharing a function name — that last one because the later
definition silently replaces the earlier in the shared file, and the first
step's tests would then be grading code written for the second.

### Playable today

`vibecoder boss w1-boss-pipeline` runs the fight step by step and **stops at the
first failure**, because a boss is a sequence: reporting step three against a
buffer whose step one is wrong grades a situation the player is not in.
`--reference` watches the fight completed, `--solution` runs a file.

Shipping it playable is what makes W1 a waypoint rather than a data structure.
Live stepping, step-back and edit-and-resume are W2–W4.

### The first boss

`w1-boss-pipeline`, three steps: parse a CSV-ish feed, drop rows under a price
floor, then summarise using both. Deliberately made of ordinary functions — the
interesting part of a boss is that the steps link, and a boss whose individual
steps were hard would test the wrong thing this early in the campaign.

## Misconceptions and corrections

### M31 — the shared state wanted a mechanism

**Believed:** "Ordered steps, per-step tests, shared state" meant the format
needed somewhere to *put* the state — a namespace threaded between steps, or
step *n*'s return value passed into step *n+1*'s tests. I started designing how
step two would receive step one's output.

**Revealed by:** Working through what happens when step one is wrong. Every
version of that design fails step three for a step-one mistake, which scores one
error three times and tells the player the wrong thing about where they went
wrong. The mechanism I was designing existed to create a problem.

**Corrected to:** The shared state is the **source file**, and it needs no
mechanism at all. The steps are functions in one module; a later step calls an
earlier one because that is what Python does. Grading stays per-step and
independent, and the unlock order means an earlier function has already passed
its own tests before anything calls it.

**Cost:** ~15 minutes of design that produced no code. Worth recording because
the waypoint's own wording ("shared state") pointed at the mechanism, and the
right answer was that the format already had one.

## Friction

- `style_goals=("comprehension",)` was wrong: the registry keys are
  `uses_comprehension` and friends. Caught immediately by the contract test
  copied from `test_levels`, which is the argument for copying it.
- Three consecutive attempts to patch `cli.py` aborted midway because a `rep()`
  helper called `sys.exit` on a missed anchor *before* the file was written, so
  earlier successful replacements were discarded silently — twice I read a
  "FAILED" line and assumed only that one edit had been skipped. Write the file
  or do not, but do not report per-edit success for edits that were then thrown
  away.

## Decisions

| # | Decision | Alternatives considered | Rationale | Reversible? |
| --- | --- | --- | --- | --- |
| D102 | Each step is graded against its own canonical tests | Feed step *n*'s output into step *n+1*'s tests | Otherwise a step-one mistake fails step three, scoring one error three times and misreporting where it happened | no — this is the format |
| D103 | The shared state is one source file, not a namespace | A threaded state object; explicit inter-step plumbing | The steps are functions in a module; a later step calling an earlier one is ordinary Python. The mechanism existed only to create the cascade problem (M31) | yes |
| D104 | Steps unlock in order | Let the player attempt any step | It is what makes calling an earlier function safe: it has already passed its own tests | yes |
| D105 | `uses` is checked against the reference, never the player | Enforce it on submissions | It documents intent and keeps the boss honest. A player who finds another way that passes has not done anything wrong | yes |
| D106 | A linked step's reference must fail in isolation | Only check that it passes in context | A reference that passes alone proves the step never needed its dependencies, and the boss is three levels wearing one name | yes |
| D107 | Two steps may not share a function name | Allow it, last definition wins | The later definition replaces the earlier in the shared file, so the first step's tests would grade code written for the second | no |
| D108 | Bosses are a separate registry from levels | One registry with a kind flag | A boss is a different shape, and every caller that walks levels would otherwise have to remember to ask which it was holding | yes |
| D109 | The fight stops at the first failed step | Report all steps every time | Reporting step three against a buffer whose step one is wrong grades a situation the player is not in | yes |
